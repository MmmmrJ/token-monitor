# Token Monitor v1.3.0 测试修复方案

> 测试日期：2026-07-27
>
> 测试基线：`codex/v1.3.0-update-diagnostics`，应用版本 `1.3.0`
>
> 结论：功能主体可用，但在修复以下发布阻断项前，不创建 `v1.3.0` Tag 或 Stable Release。

## 1. 本轮测试结果

- 设置中的“额度提醒”与“关于与诊断”区块可访问，中文 / English 文案完整。

- `npm test`：13 项通过。

- `cargo clippy --all-targets -- -D warnings`：通过。
- 非沙箱环境 `cargo test`：40 项通过。

- Windows 安装、AuthentiCode 以及可选平台签名路径尚未进行实际环境验收。

## 2. 发布阻断修复

### 2.1 移除 WebView 中的敏感身份和路径

**问题**：设置页来源卡将账户显示名、套餐和完整本机认证路径渲染给 WebView；这违反项目“Token、账户 ID、完整本机路径不得进入 WebView”的安全边界。

**修改**：

- Rust 序列化到前端的 Snapshot 改为只暴露固定来源标签：`Codex auth.json` 或 `Cursor local session`。
- 删除或忽略前端的 `account.displayName`、`account.plan` 和 `provider.authPathLabel` 渲染。
- 来源卡使用本地化通用标题：中文“本机 Codex 账户 / 本机 Cursor 账户”，English“Local Codex account / Local Cursor account”；来源详情只使用固定通用标签。
- 账户、套餐、完整路径继续仅允许在 Rust 内部 Provider 读取逻辑中存在，不能进入 snapshot、事件、诊断、日志或导出。
- 加入序列化/前端渲染测试，断言 snapshot JSON 不包含邮箱模式、绝对路径、`displayName`、`plan`、`authPathLabel`、token 或账户 ID 键。

### 2.2 修复更新确认操作区的 `hidden` 显示

**问题**：已是最新版时，“确认下载并安装 / 取消”仍可见。CSS 的 `.about-update-actions { display: flex; }` 覆盖了 `hidden` 元素的隐藏规则。

**修改**：

- 在 `styles.css` 中显式加入：

```css
.about-update-actions[hidden],
.about-update-notes[hidden],
.about-update > button[hidden] {
  display: none;
}
```

- 保持状态机语义：
  - `upToDate` / `checking` / `failed`：只显示状态文本。
  - `available`：显示 Release notes 与“下载并安装”。
  - `confirming`：仅显示确认说明、“确认下载并安装”和“取消”。
  - `downloading` / `installing`：隐藏所有可重复触发的更新按钮。
- 补充前端 DOM 测试或 CSS 回归测试，确认各状态下不应显示的控件包含 `hidden` 且最终计算样式为 `display: none`。

### 2.3 修复下载进度累计计算

**问题**：Tauri `download_and_install` 的第一个回调参数是单个分块大小；现有实现将其当成累计下载字节数，导致真实百分比错误。

**修改**：

- 在一次 `install_app_update` 调用内维护 `downloaded_total: u64`。
- 每次回调使用 `downloaded_total = downloaded_total.saturating_add(chunk_length as u64)`；计算百分比时使用 `downloaded_total / content_length` 并限制为 `0..=100`。
- `UpdateProgressEvent.downloaded` 输出累计字节数；`total` 未知时 `percent` 为 `null`，前端显示不确定下载状态。
- 下载完成回调显式发送 `100%` 或 `installing` 状态，随后才执行安装；安装失败仍保留正确错误类别。
- 新增 Rust 纯函数测试：多 chunk 累计、总量未知、总量为 0、累计超出总量、下载完成和错误分类。

### 2.4 恢复 Rust 格式门禁

**问题**：`src-tauri/src/diagnostics.rs` 与 `src-tauri/src/updater.rs` 存在 rustfmt 差异，CI 会失败。

**修改**：

- 对上述文件运行 `cargo fmt --manifest-path src-tauri/Cargo.toml`。
- 不借格式化顺便重写无关代码。
- 在提交前执行 `cargo fmt --check --manifest-path src-tauri/Cargo.toml`，确保与 Release workflow 一致。

## 3. 平台签名状态改进

### 3.1 如未配置证书

- 保持 `not_configured`，在 About 与 Release Notes 明确披露：macOS 未公证、Windows 未 Authenticode 签名；仍提供 `SHA256SUMS.txt`。
- 不将“Updater 已配置”表述为“操作系统已信任”。

### 3.2 如配置了平台凭据

- macOS：仅当 `APPLE_CERTIFICATE`、`APPLE_CERTIFICATE_PASSWORD`、`APPLE_SIGNING_IDENTITY` 和 notarization 凭据均齐全时，导入临时 keychain、签名、验证 `codesign` / Gatekeeper / notarization ticket；成功后将构建状态标记为已签名并已公证。
- Windows：仅当完整 Azure Artifact Signing 或受支持证书签名配置存在时启用签名，并验证 MSI 与 NSIS Setup EXE；成功后标记为已签名。
- 任一可选平台凭据不完整时，跳过该平台签名路径并明确显示“未配置”；不得部分执行后仍宣称已签名。
- Tauri updater 私钥继续独立于 Apple/Windows 平台凭据，并始终为 Stable Release 硬门槛。

## 4. 验证与发布流程

### 4.1 自动化

```bash
npm test
npm run check:versions
npm run build
cargo fmt --check --manifest-path src-tauri/Cargo.toml
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml
```

新增测试至少覆盖：

- Snapshot / 事件 / 诊断中不存在账户名、套餐、路径、token、账户 ID 与 URL。
- 更新状态的隐藏控件、确认取消和重复点击防护。
- 下载进度累计计算与未知总大小。
- `SHA256SUMS.txt` 覆盖所有 Release 资产，`latest.json` 只指向签名 updater 资产。

### 4.2 原生手工验收

- macOS 与 Windows：设置页滚动可完整访问提醒和关于/诊断；中英文切换后所有新文本、Title 与 aria-label 正确。
- 更新检查：无更新、网络失败、签名失败、下载中断、磁盘空间不足、安装失败均显示准确的可恢复状态。
- 使用一个私有测试 Tag 或本地签名 fixture，完成 `v1.2.0 → v1.3.0` 的真实应用内升级；确认窗口位置、语言、Provider、视图、始终置顶和提醒配置保留。
- 不在公开 Stable Release 上用生产用户执行降级、覆盖安装或未验证更新测试。

### 4.3 发布门槛

仅当以下条件同时满足时，才提交、合并、创建 annotated `v1.3.0` Tag 并发布：

1. P0 / P1 修复完成，`cargo fmt --check`、所有测试与双平台 Quality workflow 通过。
2. 应用内更新真实升级路径已在私有测试流程中通过。
3. Release 包含 DMG、MSI、NSIS Setup EXE、macOS updater archive、对应 Tauri 签名、唯一 `latest.json` 与 `SHA256SUMS.txt`。
4. About、Release Notes 和安装说明的 updater / macOS / Windows 签名状态完全一致且真实。

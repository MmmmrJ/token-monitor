# Token Monitor v1.3.0 — 更新闭环与安全诊断实施方案

> 当前基线：`v1.2.0`
>
> 建议开发分支：`codex/v1.3.0-update-diagnostics`
>
> 目标版本：`v1.3.0`
>
> 计划日期：2026-07-27

## 摘要

以已发布的 `v1.2.0` 为基线，实现可见、可控、可验证的应用内更新流程，并在设置页增加“关于与诊断”分区。

本版本不扩展 Provider、账户切换、历史 Dashboard 或浏览器 Cookie 读取；继续保持静态 HTML/CSS/JavaScript 前端，Rust 负责 updater、诊断、安全边界和原生集成。

## 1. 更新体验

### 1.1 设置入口与状态

- 设置页新增“关于与诊断”分区，显示当前版本、系统与架构、GitHub Releases、问题反馈和“检查更新”。
- 手动检查必须给出明确结果：已是最新版、发现新版本或可恢复错误。
- 保留启动后 15 秒和每天一次的后台检查；后台检查只在发现更新时提示，不打扰用户。
- 更新状态统一为：`idle | checking | upToDate | available | confirming | downloading | installing | failed`。
- 同一时间只允许一个检查或安装任务，重复操作复用当前任务或禁用控件。

### 1.2 确认、下载与重启

- 发现更新后展示目标版本、Release notes 和“下载并安装”操作。
- 点击“下载并安装”后先显示确认说明，明确下载、安装与重启影响；用户再次确认才开始。
- Rust 的 `UpdateAvailability` 扩展下载状态与可恢复错误分类。
- 安装命令通过 Tauri updater 下载进度回调发射事件；前端显示百分比或不确定进度。
- 下载完成后仅在用户已确认的流程中安装并重启；不执行静默更新。

### 1.3 失败处理

- 签名不匹配、断网、下载中断、磁盘空间不足和安装失败必须停止流程，保留当前版本。
- 错误使用双语顶部短条或控件内联状态显示；禁止 Toast。
- 用户取消确认时回到可再次检查/安装的状态，不记录失败。

## 2. 关于与安全诊断

### 2.1 原生接口

新增 Rust 命令：

```text
get_app_info
get_safe_diagnostics
```

`AppInfo` 返回：

```text
version
os
arch
releaseUrl
issueUrl
updaterSignatureStatus
platformSigningStatus
```

`SafeDiagnostics` 返回：

```text
version
os
arch
provider
availability
errorKind
cached
checkedAt
refreshedAt
hasFiveHour
hasSevenDay
sourceLabel
```

### 2.2 诊断摘要边界

- 设置页提供“复制诊断摘要”，生成中英文可读文本并复制到剪贴板。
- 复制失败时提供可选择文本的回退，不写入磁盘。
- `sourceLabel` 仅允许固定通用标签，例如 `Codex auth.json`、`Cursor local session`。
- 诊断禁止包含账户显示名、套餐、余额数值、Token、账户 ID、完整路径、请求 URL、自定义基址和原始响应。
- 序列化后必须二次检测并拒绝敏感键名、Bearer Token、JWT、账户 ID、绝对路径、URL 与额度数值；命中后不复制并显示安全错误。

## 3. 签名状态与 Release

### 3.1 应用内披露

- “关于”区域明确区分并显示：Tauri updater 签名、macOS Developer ID/公证、Windows Authenticode。
- 未配置的平台必须显示“未配置”，不得暗示已获 Apple 或 Microsoft 信任。
- Release 链接跳转 GitHub Release；问题反馈链接跳转项目 Issue 页面。

### 3.2 Release 完整性

- Release workflow 生成并上传 `SHA256SUMS.txt`，覆盖 DMG、MSI、NSIS Setup EXE、`.app.tar.gz`、签名文件与 `latest.json`。
- `latest.json` 只引用已签名的 macOS `.app.tar.gz` 和 Windows Tauri v2 updater 资产（已签名 `*-setup.exe`；若使用 `v1Compatible` 则为 `.nsis.zip`）。普通 MSI / DMG 不作为应用内 updater artifact。
- Tauri updater 签名是创建 Stable 的硬门槛。
- macOS 签名/公证仅在完整 Apple Secrets 存在时启用，并验证 `codesign`、Gatekeeper 与 notarization ticket；未配置时发布说明标记“未公证”。
- Windows Authenticode 仅在完整 Azure/证书签名配置存在时启用，并验证 MSI 与 NSIS Setup EXE；未配置时标记“未签名”。
- 平台代码签名状态与 updater 签名状态独立，不能互相替代。

Tauri 的应用内更新需要使用已签名更新产物；macOS/Windows 平台代码签名是独立机制。参阅 [Tauri macOS 签名与公证文档](https://v2.tauri.app/zh-cn/distribute/sign/macos/) 与 [Windows 代码签名文档](https://v2.tauri.app/zh-cn/distribute/sign/windows/)。

## 4. 测试与验收

### 4.1 自动化测试

- 前端：手动检查、后台检查不打扰、版本可用、确认取消、下载进度、全部失败状态、中英文、键盘焦点。
- Rust：`AppInfo` 平台映射、诊断白名单、敏感键名/Bearer/JWT/路径/URL/额度拦截、无可用更新、更新错误分类。
- Release fixture：唯一 `latest.json`、Windows 更新 URL 指向已签名 `*-setup.exe`（或兼容 `.nsis.zip`）、签名齐全、所有安装资产都有 SHA-256。
- 继续执行既有前端、Rust、版本一致性、构建、Clippy 与双平台 Release CI。

### 4.2 升级与原生验收

- 在 `v1.2.0` 安装实例上验证应用内升级到 v1.3.0。
- 升级后保留窗口位置、语言、Provider、视图、始终置顶和提醒配置。
- `v1.1.2` / `v1.1.3` 通过手动安装升级到 v1.3.0，设置仍保留。
- 签名不匹配、断网、下载中断均不得安装，并显示可恢复错误。
- 只有 updater 签名、全部资产、`SHA256SUMS.txt` 和签名状态披露完整后，才创建 `v1.3.0` Tag 与 Stable Release。

## 5. 默认约束

- 仅提供 Stable 通道；Beta 通道延后。
- 不新增第三个 Provider、多账户、手填 Token、浏览器 Cookie、Token/费用历史、大型趋势 Dashboard 或多设备同步。
- 保持现有隐私边界：Token、账户 ID、原始响应和完整本机路径不得进入 WebView、日志、导出、诊断或仓库。
